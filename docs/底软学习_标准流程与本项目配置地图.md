# S32K144 转向灯项目：底软标准开发流程与实际配置地图

工程：`G:\S32K144_Start_TurnLight_IAR_20260912\S32K144_Start_new_IAR`

## 0. 先判断工程所处状态

本工程不是空白工程。它已经包含：

- `Config\ECUC\`：Configurator 导出的 ECUC/MCAL/BSW 配置
- `Config\Developer\`：SWC、接口、数据类型和 RTE 设计输入
- `Appl\GenData\`：Configurator/ RTE 生成的 C、H 文件
- `MCAL\`、`BSW\`：供应商底软源码
- `ASR_S32K144_Start.ewp`、`IarStartApp.ewp`：IAR 工程

因此学习时分两条线：

1. **逆向理解**：从 ARXML 和生成代码还原“在 Configurator 中配置了什么”。
2. **正向实验**：复制工程后只改一个参数，重新生成、编译、烧录，再用 IAR/TSMaster 验证。

每次改配置前先备份 `Config\ECUC`、`Config\Developer` 和 `Appl\GenData`。

## 1. 标准的自底向上流程

```text
原理图/芯片手册
    ↓
Mcu（时钟、复位、低功耗）
    ↓
Port（引脚复用、方向、上下拉、初始电平）
    ↓
Dio（给 GPIO 分配可读的逻辑通道）
    ↓
SysTick/OS/EcuM（1 ms 心跳、任务、启动顺序）
    ↓
Can + CanIf（控制器、波特率、HOH、PDU ID）
    ↓
PduR + Com（PDU 路由、信号打包/解包、周期发送）
    ↓
Developer + Rte（SWC、Runnable、端口、任务映射）
    ↓
生成代码 → IAR 编译 → 烧录 → CAN/LED/调试验证
```

工程实践中，每一层都要完成“输入、配置、生成、验证”四件事，不能只在界面里点完参数就认为完成。

## 2. 本项目的硬件和信号基线

### 2.1 MCU 时钟

实际配置文件：`Config\ECUC\S32K144_Start_Mcu_ecuc.arxml`

| 参数 | 当前值 | 含义 |
|---|---:|---|
| 外部 SOSC 输入 | 8 MHz | 板上外部时钟/晶振输入 |
| SPLL 输入 | 8 MHz | 使用 SOSC 作为 PLL 输入 |
| SPLL 倍频 | 40 | 得到 160 MHz PLL 内部时钟 |
| 系统时钟源 | SPLL | `McuSystemClockSwitch = SPLL` |
| Core 时钟 | 80 MHz | `McuCoreClockFrequency = 80000000` |
| Bus 时钟 | 40 MHz | `McuBusClockFrequency = 40000000` |
| Flash 时钟 | 20 MHz | `McuFlashClockFrequency = 20000000` |
| LPSPI1 时钟 | 40 MHz | 外设时钟选择 SPLL |
| McuInitClock | true | 启动时执行时钟初始化 |
| McuNoPll | false | 使用 PLL |

S32K144 这里使用 80 MHz 系统/核心时钟，不能照搬“112 MHz”的通用示例。

### 2.2 Port 引脚

实际配置文件：`Config\ECUC\S32K144_Start_Port_ecuc.arxml`

| 引脚 | 复用 | 方向 | 初始电平 | 用途 |
|---|---|---|---|---|
| PTD0 | GPIO | OUT | HIGH | FL，板上 LED2 |
| PTD1 | GPIO | OUT | HIGH | FR，板上 LED3 |
| PTD15 | GPIO | OUT | HIGH | RL，板上 LED4 |
| PTD16 | GPIO | OUT | HIGH | RR，板上 LED5 |
| PTE4 | CAN0_RX | IN | - | CAN 接收 |
| PTE5 | CAN0_TX | OUT | - | CAN 发送 |
| PTB14 | LPSPI1_SCK | OUT | - | SPI 时钟 |
| PTB15 | LPSPI1_SIN | IN | - | SPI 输入 |
| PTB16 | LPSPI1_SOUT | OUT | - | SPI 输出 |
| PTB17 | LPSPI1_PCS3 | OUT | - | SPI 片选 |

PTD0/PTD1/PTD15/PTD16 的初始电平是 HIGH，和 LED 的实际有效电平、板级连接有关。不能仅凭“GPIO 输出高就是灯亮”判断逻辑，必须结合原理图和 `Cdd_IoHwAb.c` 验证。

### 2.3 Dio 通道

实际配置文件：`Config\ECUC\S32K144_Start_Dio_ecuc.arxml`

| Dio 符号 | 芯片通道 | 应用用途 |
|---|---:|---|
| `DioChannel_PTD0` | 0 | FL |
| `DioChannel_PTD1` | 1 | FR |
| `DioChannel_PTD15` | 15 | RL |
| `DioChannel_PTD16` | 16 | RR |

应用层通过生成的符号调用，例如：

```c
Dio_WriteChannel(DioConf_DioChannel_DioChannel_PTD0, CtrlCmd);
```

Port 决定“这个引脚是什么电气功能”，Dio 决定“应用用哪个逻辑名字访问它”。

## 3. 第一阶段：Mcu 配置与点亮最小系统

### 3.0 在 Configurator 界面中的实际操作路径

1. 关闭旧的 Configurator 窗口，双击工程目录中的 `OpenConfigurator.bat`。
2. 等待项目加载完成，左侧选择 **Configuration Editors**。
3. 在模块树中展开供应商 MCU 模块（通常显示为 `Mcu` 或 `Mcu_TS_T40D2M10I1R0`）。
4. 进入 `McuModuleConfiguration`，再进入 `McuClockSettingConfig_0`。
5. 按以下顺序配置：

```text
McuGeneralConfiguration
McuModuleConfiguration
  └─ McuClockSettingConfig_0
       ├─ McuFIRCClockConfig
       ├─ McuSIRCClockConfig
       ├─ McuSystemOSCClockConfig
       ├─ McuSystemPll
       ├─ McuRunClockConfig
       ├─ McuHsrunClockConfig
       └─ McuPeripheralClockConfig
```

6. 修改一个参数后先按 `Ctrl+S`，再点击工具栏的 **Validate**；确认没有红色错误后再进行下一项。
7. 本次学习只保存当前配置，不点击 Generate，避免改变已经可以编译的生成代码。

Configurator 中带有“计算结果”性质的频率字段通常由输入频率、倍频和分频自动计算。若某个频率字段不可编辑，应修改它对应的时钟源或 Divider，而不是强行改计算结果。

### 3.1 配置目标

在 Configurator 中打开 Mcu 模块，先只关心：

1. 芯片型号/Derivative 与实际器件一致。
2. SOSC 输入频率与板上硬件一致：本项目 8 MHz。
3. SPLL 使能、输入源、倍频和分频正确。
4. Core/Bus/Flash 频率满足 S32K144 规格。
5. 启用 `McuInitClock`，保留一个 RUN 模式。

当前工程的关键结果是：SPLL 内部 160 MHz，Core 80 MHz，Bus 40 MHz，Flash 20 MHz。

### 3.2 为什么这些参数重要

- CAN 波特率计算依赖外设/系统时钟。
- OS 的 SysTick 每 tick 计数值依赖 Core 时钟。
- SPI 分频依赖 LPSPI 外设时钟。
- 频率错了，CAN 可能完全收不到，OS 周期也会偏移。

### 3.3 生成和验证

生成后重点查看：

- `Appl\GenData\Mcu_PBcfg.c`
- `Appl\GenData\Mcu_Cfg.h`
- `MCAL\Mcu_*\generate_PC\`

IAR 中设置断点观察：

```text
Mcu_Init()
Mcu_InitClock(0)
Mcu_DistributePllClock()
```

验收顺序：

1. 能执行到 `Mcu_Init()`。
2. 能执行到 `Mcu_InitClock(0)`。
3. PLL 锁定后不进入错误处理。
4. 后续 SysTick 计时接近 1 ms。

本项目没有把“示波器测晶振脚”作为主要验收手段；更实际的做法是用 IAR 观察时钟初始化寄存器和 OS tick，再用周期 GPIO 翻转测量 1 ms/10 ms。

## 4. 第二阶段：Port/Dio 配置与 GPIO 验证

### 4.1 Port 的配置层次

每个 PortPin 至少检查：

- `PortPinId`：物理 pin 编号
- `PortPinMode`：GPIO、CAN0_RX、CAN0_TX、LPSPI1 等复用功能
- `PortPinDirection`：输入或输出
- `PortPinInitialMode`：启动模式
- `PortPinLevelValue`：初始化电平
- `PortPinPE`：上下拉使能
- `PortPinPS`：上拉/下拉选择
- `PortPinDSE`：驱动强度
- `PortPinPFE`：数字滤波/输入滤波

### 4.2 本项目四路 LED

配置 PTD0、PTD1、PTD15、PTD16 为：

```text
Mode = GPIO
Direction = OUT
Initial mode = GPIO
Initial level = HIGH
Pull = Disabled
```

Dio 再为这四个引脚创建符号通道。`Cdd_IoHwAb.c` 将 FL/FR/RL/RR 的命令写入这四个通道。

### 4.3 第一个独立实验

在应用任务中临时加入一个可逆测试：每 500 ms 对 PTD0 取反。

```c
static uint8 testState = 0u;
testState = (uint8)!testState;
Dio_WriteChannel(DioConf_DioChannel_DioChannel_PTD0, testState);
```

验证点：

- IAR 能看到测试函数周期执行。
- LED2 或 PTD0 电平每 500 ms 翻转。
- 逻辑分析仪测得周期约 1 s（高、低各 500 ms）。

完成后撤销临时代码，避免干扰转向灯逻辑。

## 5. 第三阶段：OS、SysTick 与 EcuM

### 5.1 本项目的真实实现

实际文件：`Config\ECUC\S32K144_Start_Os_ecuc.arxml`

本项目使用：

| 项目 | 当前值 |
|---|---|
| Counter | `SystemTimer` |
| 类型 | HARDWARE |
| `OsSecondsPerTick` | 0.001 s |
| `OsCounterTicksPerBase` | 80000 |
| 硬件通道 | S32K148 SysTick Ch0 |
| BSW 任务 | `OsTask_BSW_SCHM`，优先级 10 |
| APP 任务 | `OsTask_APP`，优先级 15 |

80 MHz / 80000 = 1 kHz，因此一个 tick 是 1 ms。

这里没有以 GPT 模块作为系统节拍源。GPT 可以用于独立定时器场景，但不能把“标准流程示例中的 GPT”误认为“本工程已经使用 GPT”。

### 5.2 周期 Runnable 的关系

当前转向灯三个应用 SWC 的 Runnable 都是 10 ms：

- `TurnLightArb`：`TMT_TurnLightArb_Runnable_10ms`
- `TurnLightAct`：`TMT_Runnable_10ms`
- `TurnLight`：`TMT_TurnLight_Runnable_10ms`

它们通过 RTE 映射到 `Rte_Ev_Cyclic_OsTask_BSW_SCHM_0_10ms`，再由 `Rte_Al_TE_OsTask_BSW_SCHM_0_10ms` 关联到 OS 任务。

因此课件中出现的 100 ms、300 ms 可能是功能计时或另一版本工程的周期，不能直接说本工程已经创建了 100 ms/300 ms OS 任务。要新增它们，需要在 Developer 中新增 TimingEvent，再在 Configurator/OS 中生成对应 Alarm/Event/Task 映射。

### 5.3 验收

1. 断点观察 `StartOS()`。
2. 观察 `OsTask_BSW_SCHM` 被激活。
3. 在 10 ms Runnable 入口设置 GPIO 翻转或 IAR 计数器。
4. 用逻辑分析仪测量 10 ms 周期。

### 6.1 Can 驱动配置

| 参数 | 当前值 |
|---|---:|
| 控制器 | FlexCAN0 |
| Controller ID | 0 |
| 激活 | true |
| 波特率 | 500 kbit/s |
| CAN 时钟 | 80 MHz |
| Prescaler | 8 |

| SJW | 1 |

注意：Can 驱动中的 `CanIdValue=0` 或 `CanObjectId` 是硬件对象/邮箱配置的一部分，不等于最终总线上的 CAN ID。最终 0x210/0x200 在 CanIf PDU 中配置。

### 6.2 CanIf 配置

实际文件：`Config\ECUC\S32K144_Start_CanIf_ecuc.arxml`

本项目关键 PDU：

| 方向 | PDU | 十进制 ID | 十六进制 ID | DLC |
|---|---|---:|---:|---:|
| Rx | `msg_Receive_oCAN00` | 528 | 0x210 | 8 |
| Tx | `msg_Transmit_oCAN00` | 512 | 0x200 | 2 |

诊断 PDU 还包括 0x610/0x612 等 ID，但转向灯实验主要使用 0x210 和 0x200。

### 6.3 验收

- TSMaster 发送 `0x210`、DLC 8，板子能改变 LED 状态。
- TSMaster 能收到 `0x200`、DLC 2。
- IAR 可在 `CanIf_RxIndication`、`PduR_CanIfRxIndication` 观察接收链路。

## 7. 第五阶段：PduR 与 Com

### 7.1 PduR 的作用

实际文件：`Config\ECUC\S32K144_Start_PduR_ecuc.arxml`

对于普通通信报文，链路是：

```text
Can → CanIf → PduR → Com → RTE/SWC
SWC/RTE → Com → PduR → CanIf → Can
```

PduR 不解释信号含义，只根据 RoutingPath 把一个 PDU 从源模块转发到目标模块。本项目普通 0x210/0x200 报文使用 `COMMUNICATION_INTERFACE`，并采用立即转发。

### 7.2 Com 的 0x210 接收信号

实际文件：`Config\ECUC\S32K144_Start_Com_ecuc.arxml`

| 信号 | 起始位 | 长度 | 类型 |
|---|---:|---:|---|
| CrashIntensity | 3 | 1 | BOOLEAN |
| EmergencyBrakeLight | 4 | 1 | UINT8 |
| VehicleSpeed_Valid | 5 | 1 | UINT8 |
| HazardSw | 8 | 4 | UINT8 |
| IGN_Status | 12 | 4 | UINT8 |
| TurnLampFb_FL | 16 | 4 | UINT8 |
| TurnLampFb_FR | 20 | 4 | UINT8 |
| TurnLampFb_RL | 24 | 4 | UINT8 |
| TurnLampFb_RR | 28 | 4 | UINT8 |
| TurnLampSw | 32 | 4 | UINT8 |
| VehicleSpeed | 40 | 8 | UINT16 |

### 7.3 Com 的 0x200 发送信号

| 信号 | 起始位 | 长度 | 类型 |
|---|---:|---:|---|
| `LA_St_DirectionLampL` | 1 | 4 | UINT8 |
| `LA_St_DirectionLampR` | 8 | 4 | UINT8 |

Tx PDU 配置为周期发送，工程中主要周期是 100 ms。`ComIPduSignalProcessing=DEFERRED` 表示信号处理由 Com 主函数完成，不是在接收中断里直接执行完整应用逻辑。

### 7.4 为什么 TSMaster 发一帧后状态可能保持

Com 接收信号写入缓冲区后，应用 Runnable 会周期读取它。停止发送并不自动把最后一次接收值清零，除非配置了 Rx deadline monitoring、超时回调或应用显式复位。因此实验时要区分：

- “总线上是否还有报文”；
- “Com 缓冲区中最后一次有效值”；
- “应用状态机是否在等待下一次输入”。

## 8. 第六阶段：Developer、RTE 和底软连接

Developer 文件：

- `Config\Developer\DataTypes.arxml`
- `Config\Developer\PortInterfaces.arxml`
- `Config\Developer\ComponentTypes\TurnLight.arxml`
- `Config\Developer\ComponentTypes\TurnLightArb.arxml`
- `Config\Developer\ComponentTypes\TurnLightAct.arxml`
- `Config\Developer\S32K144_Start.dcf`

三个应用 SWC 的作用：

```text
TurnLightArb：仲裁输入和优先级，决定左/右/双闪等目标状态
TurnLight：执行闪烁、计时、短按三闪等灯光策略
TurnLightAct：把目标状态转成四路执行命令
Cdd_IoHwAb：调用 Dio_WriteChannel，落到 PTD0/PTD1/PTD15/PTD16
```

Configurator 中的 RTE 配置文件是：`Config\ECUC\S32K144_Start_Rte_ecuc.arxml`。它把 SWC 的 TimingEvent、Runnable 和 OS Alarm/Event/Task 串起来。RTE 不负责生成 CAN 波特率，也不负责配置 PTD0，它负责把软件接口连接到对应的任务和 BSW 服务。

| 阶段 | 主要输入 | 主要配置 | 生成/检查文件 | 板上验收 |
|---|---|---|---|---|
| Mcu | 芯片手册、晶振参数 | SOSC/SPLL、分频、RUN 模式 | Mcu_PBcfg.c | 时钟初始化、tick |

## 10. 推荐的实际学习顺序

### 实验 1：只验证 Mcu + OS

不改 CAN 和应用逻辑，在 10 ms Runnable 中翻转一个未使用测试 GPIO，确认周期。

### 实验 2：只验证 Port + Dio

让 PTD0 固定输出 0/1，确认 LED2 与 IAR 观察值一致。

### 实验 3：只验证 CAN/CanIf

保持应用层不变，用 TSMaster 发送 0x210，先在 IAR 断点确认 Rx 回调被调用。

### 实验 4：验证 Com 位定义

只改变 0x210 的一个信号，例如 `TurnLampSw`，观察对应 Com 变量是否变化。

### 实验 5：验证 RTE 到 Dio

沿调用链单步：

```text
TurnLight Runnable
 → Rte_Call/Rte_Read/Rte_Write
 → Cdd_IoHwAb
 → Dio_WriteChannel
 → PTD pin
```

### 实验 6：再做配置修改

例如把 0x200 周期从 100 ms 改为 200 ms，生成、编译、烧录，用 TSMaster 测量周期变化。

## 11. 与简历的对应关系

这个项目更能体现的底软工作是：

- NXP S32K14x MCU 时钟、Port、Dio、CAN、LPSPI 的 Configurator 配置
- CAN/CanIf/PduR/Com 通信栈集成
- Developer 中 SWC/RTE 接口和 Runnable 到 OS 的映射
- IAR 联合编译、断点调试和生成代码问题定位
- TSMaster、逻辑分析仪、板上 LED 联调

不要把当前教学板描述成完整量产 ECU：课件中的 AD 转向开关、HSD 负载、完整故障诊断和后视镜灯并没有全部在这块板上实现。简历表述应限定为“基于 CAN 模拟输入、GPIO LED 输出完成教学 ECU 联调”。
